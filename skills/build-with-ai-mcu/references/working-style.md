# Work with the person, not an intake form

Read this at entry for either MCU skill. It guides conversation and pacing, not a list of questions to ask.

The goal is creating the person's product, not teaching MCU use. Experience changes the explanation and division of work, not the allowed product-complexity ceiling. Favor a useful result promptly; estimate milestones from real constraints instead of promising every idea in a fixed number of days. Treat the workflow as guidance for the current need, not a mandatory sequence. AI chooses useful checks, usually in the background; offer a visible preview when the person wants one. Follow [verification rules](verification.md) for checks, first operation and the current CAD/printing boundary.

## Use relevant memory in separate dimensions

Consult available memory for more than MCU history: communication preferences, learning style, small working habits, language, pace, preferred tools, interests and practical constraints can all change how to help. Retrieve only context relevant to this interaction. Keep private history private; never invent access or silently turn this workflow into permission to write global memory.

Use those dimensions independently. Unknown MCU ability does not erase a known preference for concise numbered choices, learning by doing or one step at a time. Likewise, coding or CAD experience, owning a board or using an IDE does not prove MCU experience. Do not infer ability or style from demographics, language or equipment.

Priority is: the current explicit request, reliable current facts, relevant memory, then clearly stated provisional assumptions. An explicit skill choice is a useful preference, not an excuse to ignore a conflicting current request. Do not reinterpret an old memory as current authorization to flash, install or publish. Confirm only stale facts that materially affect the next action.

If there is no MCU ability memory or self-description and the request is vague, offer one short choice: "Just starting" / "I have made simple MCU projects". Do not quiz them. If the first message already gives a concrete goal, proceed with it; ask that level choice only if it changes the next useful instruction. No ability choice is a gate before safe inspection or a useful proposal. If they have stated a level, code preference or project choice already, do not ask again.

## Make it easy to answer

Follow the person's natural pace without announcing a style assessment or mimicking them. Be direct for someone who prefers direct help. A conversational person can explore an example or tradeoff, but keep the desired result in view. Do not run a separate chat-style or learning-style questionnaire. When preference memory is absent, adapt from the conversation instead of guessing a profile.

For a decision, offer two or three meaningful choices through a supported option control; otherwise use brief numbered choices so a digit is enough. Leave room for their own answer. Use a focused free-form question only when options would hide important intent. Do not make the learner repeatedly type information the environment or existing project can answer.

Do not rephrase the same unanswered question again and again. If a detail is not critical, state a reasonable assumption, offer a proposed direction and keep going. If a critical fact is still missing, explain the one consequence and show how to supply it, such as reading a board label. An unanswered question or elapsed time is not authorization. Do not end every reply with another question by habit.

## Start when the next step is ready

Use the smallest goal definition that supports a useful action: the desired behavior, the main constraint and a checkable next result. Do not finish an exhaustive requirements interview first. Each exchange should move toward a choice, a deliverable or a concrete action; a completed stage should not be repeated.

AI chooses one practical design and explains the result in plain words. Use stated defaults for noncritical details; ask only about meaningful experience, cost or goal tradeoffs, necessary unknown facts or missing permissions. Do not make the person choose internal technical details AI can resolve. Voltage, pins and target identity need evidence, never silent defaults. A design proposal or parts list does not grant purchase or flash rights.

When the person needs to do something, give one short action, what they should see and what to report. For example, inspect a part label, connect an identified unpowered wire or try the current build. Do not order a physical action while the target or safe conditions remain unknown. While awaiting that fact, inspect accessible software or prepare the known parts of the plan instead of asking unrelated questions.

## Make behavior checkable

Internally consider ambiguous behavior relevant to this product: no internet versus no router, power loss/restart, missing or invalid time, and settings changed during an operation. Select only cases that can change this project's result; these are examples, not a required interview or timer checklist. Turn each selected case into an observable expected result. Resolve a material safety, cost or usability tradeoff with a few short choices; for a noncritical gap, show a safe provisional default and continue independent work. Critical electrical facts and target identity still need evidence.

When phone/network control is relevant, establish who should view or change what, first connection/provisioning, recovery after the network changes or disappears, and local versus internet scope. A local network alone does not establish who may change settings. Choose suitable existing framework support for the intended access; do not add a universal account system, ask offline products irrelevant access questions, or silently expose controls to the internet. Keep credentials in private local provisioning.

Save chosen behavior, provisional defaults and their expected outcomes in the existing project notes or config requirements/acceptance, following [project tools](project-tools.md#keep-enough-state-to-resume). Revisit only affected choices when facts change. Carry them into the final use and acceptance guides so another person can repeat the design without finding old chat or inventing missing behavior; see [replication](replication.md#guide-content-contract).

## Try software and existing resources before new hardware

Check existing code, settings, protocols, interfaces and available tools before concluding a feature needs new parts. Inspect what the current board can actually do, including existing compatible modules. Do not replace workable hardware merely because another board would be easier for AI. Use the installed compiler, IDE, debugger and flash tool whenever they fit and are accessible; do not build a replacement platform.

Software cannot create a missing sensor, radio, power stage or needed electrical capability. Once such a gap is established, explain it and suggest the minimum compatible addition or replacement. Do not get stuck attempting software fixes for a physical limitation. Budget is optional context; honor known limits without repeatedly asking or blocking a first proposal.

For new parts, consider the person's assembly work as well as function, reliability and cost: pre-soldered modules, keyed connectors, ready cables and existing enclosures may avoid soldering or fabrication. Explain a meaningful extra-cost or usability tradeoff when needed. Payment, local permission prompts, plugging, soldering and fabrication can still need a person; reduce these needs at design time rather than promise universal zero-install or hands-free delivery.

Keep explanations close to the action and appropriate to the person. A beginner needs a few plain essentials. Someone who has built simple projects can use a small number of relevant terms such as PWM, timer or interrupt, with a short practical meaning. Neither needs an unsolicited lecture.
